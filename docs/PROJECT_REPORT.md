## 1. What the project is

CyberSathi is a bilingual (English + Tamil) cyber-fraud awareness system with two halves that
depend on each other:

- **Working software** that analyses suspicious messages, links and payment codes, and explains
  in plain language *why* something is dangerous.
- **A measurement instrument** that runs a pre-test before an awareness workshop and a post-test
  after it, and computes whether the session actually taught anything.

The second half is what makes it a Community Service Project rather than a software project.
The software exists to cause a change; the assessment exists to prove whether it did.

**The defining constraint:** everything runs on one laptop with no internet connection and no
API key. Not as a cost saving — because the intended venue is a village hall, a school without
Wi-Fi, or a senior-citizens' hall where the projector works and the network does not.

---

## 2. The problem it addresses

Cyber-fraud in India disproportionately targets people with the least ability to recover from
it: senior citizens, rural residents, first-time smartphone users, students and homemakers
seeking income.

Existing awareness material has four gaps this project closes:

| Gap | How CyberSathi addresses it |
|---|---|
| **English-only** | Every string, article, quiz question and explanation exists in Tamil too |
| **Needs internet** | Runs entirely offline; a service worker caches the learning material |
| **Explains nothing** | Every verdict carries a plain-language reason, not just a score |
| **Measures nothing** | Matched pre/post tests with statistical analysis |

## 5. The seven modules, and how each works

### Module 1 — Scam Message Analyzer

**Endpoint:** `POST /api/v1/scam/analyze`

**Pipeline:**

```
text → detect language → REDACT PII → rule engine ─┐
                                ↓                  ├→ hybrid score → label → explanation
                            ML classifier ─────────┘
```

**Scoring is a hybrid**, not a pure model output:

```
risk_score = 0.55 × P(scam | ML)  +  0.45 × rule_score
```

Labels: `< 35` safe · `35–69` suspicious · `≥ 70` high risk.

**Why rules get 45%** — a machine-learning model cannot explain itself to a 70-year-old, and it
is limited to the distribution it was trained on. Each of the 33 rules carries its own
explanation in both languages, so every verdict is justified in a sentence the user understands.
A scam script invented tomorrow trips a rule before it ever reaches training data.

**Rule scoring uses saturating addition**, not a plain sum:

```python
score, remaining = 0.0, 1.0
for w in sorted(positive_weights, reverse=True):
    score += w * remaining
    remaining = 1.0 - score
score = max(0.0, score - negative_weights)
```

A plain sum would let five weak signals reach certainty. Saturating addition means each extra
signal contributes less. **Negative-weight rules** (legitimacy signals such as *"do not share
this OTP with anyone"*) subtract — which is how a genuine bank alert scores 0 despite containing
the word "OTP".

**Category routing:** a rule with weight ≥ 0.9 overrides the model's category. The model folds
digital-arrest messages into the broad "impersonation" class; the rule is more precise, and the
category decides which article the user is sent to.

### Module 2 — Phishing URL Checker

**Endpoint:** `POST /api/v1/url/check`

Random Forest over **25 static features** computed from the URL string:

| Group | Features |
|---|---|
| Structure | length, hostname length, path depth, dots, hyphens, subdomains, port, TLD length |
| Content | digits, digit ratio, special characters, longest token, query parameters |
| Deception | IP host, `@` trick, punycode, typosquat (Levenshtein ≤ 2), hyphen in domain, double slash |
| Reputation | suspicious TLD, shortener, brand keyword, sensitive word (`login`/`verify`/`kyc`) |
| Randomness | Shannon entropy of the hostname |

> **The URL is never fetched.** Two reasons: fetching confirms to the attacker that a human read
> the message, marking the number as live; and it risks executing a drive-by payload on a
> student's laptop during a demo. Stored URLs are **defanged** (`hxxp://`, `example[.]com`) so
> nobody can click one from the database or a report.

### Module 3 — QR / UPI Safety

**Endpoints:** `POST /api/v1/qr/analyze`, `GET /api/v1/qr/scenarios`

Parses `upi://` deep links and flags: collect/mandate intent, pre-filled amounts, payee-name ↔
VPA mismatch, look-alike Unicode characters, embedded URLs, `.apk` downloads, credential requests.

Every response carries the golden rule that prevents most UPI fraud in India:

> **Scanning a QR code or approving a request is ALWAYS to PAY.
> You never scan, and never enter a PIN, to RECEIVE money.**

**QR decoding is client-side** via jsQR — the image never leaves the device. It uses a fallback
ladder (native size → downscales at 1600/1000/640/400 → upscale → centre crops, each with a
contrast-stretched retry and both inversion attempts), because a single naive pass fails on
real photographs. Measured: a 12.2-megapixel washed-out photo returns `null` on one pass and
decodes on the ladder.

Plus **10 interactive scenarios** — refund QR, marketplace advance, fuel-pump tampering,
screen-share, and others — each with three choices, feedback and a lesson, in both languages.

### Module 4 — Cyber-Fraud Knowledge Base

**12 bilingual articles** covering all 8 required categories plus `digital_arrest`,
`courier_parcel` and `lottery`. Each article has:

- Title, summary and a 250+ word body in **both** languages
- 5–8 red flags, 5–8 safe actions, victim steps — all bilingual
- An anonymised real-world example composed from published fraud patterns
- Helpline, severity, tags

Search queries **both languages simultaneously**, because a user may type Tamil while the
interface is in English. Articles have a "Read aloud" button using the browser's speech
synthesis in `ta-IN` / `en-IN`, and a print-as-poster option.

### Module 5 — Multilingual AI Assistant

**Endpoint:** `POST /api/v1/assistant/ask`

An **eight-step resolution order**, ordered by urgency:

| # | Step | Handles |
|---|---|---|
| 1 | **Safety gate** | Refuses scam-generation and hacking requests. Wins over everything |
| 2 | **EMERGENCY** | "I lost money", "I shared my OTP" → golden-hour steps, flagged `urgent` |
| 3 | **Pasted content** | A message or link → routed to Module 1 or 2 |
| 4 | **Procedural / social** | report · helpline · greeting · thanks · about |
| 5 | **Keyword routing** | Brand and platform names → the right article, deterministically |
| 6 | **TF-IDF retrieval** | Cosine similarity, with the query expanded by topic keywords |
| 7 | **Optional local LLM** | Ollama, grounded strictly in the retrieved article |
| 8 | **Honest fallback** | Says what it *can* answer instead of shrugging |

Steps 1–6 and 8 are fully deterministic, so the assistant works with no model, no key and no
internet. **It retrieves rather than generates**, so it cannot invent a helpline number.

Two design points:

- **EMERGENCY outranks a pasted message.** Someone who has already lost money needs the steps
  that still work, not an explanation of how the scam operated.
- **A hypothetical is not an emergency.** *"What happens if someone asks for my OTP"* must not
  trigger the red alarm; a guard clause demotes hypothetical phrasing.

The interface adds voice input (`ta-IN` / `en-IN`), read-aloud, quick actions (a real `tel:1930`
button), contextual follow-up questions, and a conversation that survives a page reload.

### Module 6 — Awareness Assessment

```
setup → pre-test → result → AWARENESS CAMPAIGN → post-test → improvement
                            ↑ the intervention being measured
```

**48-question bilingual bank** across 13 categories and three difficulty levels.

**Matched but disjoint question sets.** The pre-test and post-test cover the *same category
profile* with *different questions*, sampled deterministically per `(workshop, participant)`:

- Same categories — otherwise you compare difficulty, not learning
- Different items — otherwise the post-test measures recall of the paper
- Deterministic — reloading does not reshuffle the paper

Measured item overlap: **0 of 10**, asserted by test.

**The campaign step** is personalised: the pre-test returns the participant's weak categories,
so those topics are pulled to the top and tagged *Priority*, each linking to the article to
teach from.

### Module 7 — Community Impact Dashboard

**Endpoints:** `GET /api/v1/dashboard/summary`, `GET /api/v1/dashboard/export?format=csv|json|pdf`

Reports totals, awareness change, per-category and per-demographic breakdowns, risk
distribution, activity timeline and feedback — with CSV, JSON and a printable **PDF impact
report** for the project appendix.

### Plus: Admin console

`/admin`, administrators only — account creation, role changes, enable/disable, knowledge-base
overview with read counts, and live model status with the synthetic-data caveat shown inline.

## 6. Machine learning: data, training, results

### Datasets

Both datasets are **synthetic**, generated by `ml_training/generate_datasets.py` from templates
composed from publicly documented fraud patterns (cybercrime.gov.in advisories, RBI/NPCI
awareness material, CERT-In notes). **No real victim message and no live malicious domain is
included** — a deliberate ethical and legal choice. The generator is seeded, so the datasets and
therefore the metrics are reproducible.

| Dataset | Rows | Balance | Languages |
|---|---|---|---|
| `scam_messages.csv` | 850 | 423 scam / 427 legitimate | 552 English, 298 Tamil + Tanglish (35%) |
| `urls.csv` | 815 | 381 phishing / 434 safe | — |

### Model 1 — Scam text classifier

**Vectoriser:** a `FeatureUnion` of word TF-IDF (1–2 grams, max 20,000 features) and character
TF-IDF (`char_wb`, 3–5 grams, max 30,000). Character n-grams are what make Tamil morphology and
Tanglish spelling variation (`pannunga` / `panunga`) work without a stemmer.

**Classifier:** Logistic Regression, `class_weight='balanced'`, tuned by 5-fold `GridSearchCV`
on `C`, then wrapped in `CalibratedClassifierCV` — the score is shown to users as a number out
of 100, so an uncalibrated margin would be misleading.

| Metric | Value |
|---|---|
| Test accuracy | 0.9941 |
| Test macro-F1 | 0.9941 |
| 5-fold CV macro-F1 | 0.9988 ± 0.0024 |
| **Category model** (12 classes) accuracy | 0.9647 |
| Category macro-F1 | 0.9476 |

### Model 2 — Phishing URL classifier

**Classifier:** Random Forest, `class_weight='balanced'`, tuned by 5-fold `GridSearchCV` over
`n_estimators`, `max_depth`, `min_samples_leaf`. Chosen over Logistic Regression because the URL
signals interact non-linearly — an IP host is damning alone, a hyphen only matters alongside a
brand keyword — and feature importances map cleanly onto the "why" shown to the user.

| Metric | Value |
|---|---|
| Test accuracy | 1.0000 |
| Test macro-F1 | 1.0000 |
| ROC-AUC | 1.0000 |
| 5-fold CV macro-F1 | 0.9975 ± 0.0030 |

Top features: `sensitive_word_hit`, `num_hyphens`, `suspicious_tld`.

### ⚠️ How to read these numbers — state this in your viva

**These scores are an upper bound, not expected field accuracy.**

1. **The corpus is synthetic.** Template-generated classes are far more separable than real
   traffic, which is why the figures approach 1.00.
2. **Held-out does not mean independent.** The test split comes from the same generator as the
   training split. It measures whether the model learned the generator's patterns.
3. **One data leak was found and removed.** An earlier generator gave phishing URLs `http://`
   and safe URLs `https://`, letting the model reach 100% on the `is_https` feature alone. The
   generator now makes phishing URLs predominantly HTTPS — both more realistic (free
   certificates are universal) and free of the shortcut. `is_https` no longer appears among the
   top features, which is the evidence the fix worked.
4. **This is why the system is a hybrid.** The rule engine carries 45% of the scam score and
   does not depend on the training distribution at all.

**To strengthen this for submission:** collect a small *real* validation set (100–200 messages)
donated with consent at workshops, label it by hand, and report accuracy on that separately.
Even 100 real messages is a far more credible number than 850 synthetic ones.

## 7. Privacy and security engineering

### PII redaction — before anything is stored

Every submitted text passes through `app/ml/redaction.py` **before** it reaches the database, a
log line, or an API response:

| Type | Example input | Stored as |
|---|---|---|
| OTP | `OTP is 483920` | `[REDACTED_OTP]` |
| Card number | `4532015112830366` | `[REDACTED_CARD]` |
| Aadhaar | `4123 4567 8901` | `[REDACTED_AADHAAR]` |
| Phone | `9876543210` | `[REDACTED_PHONE]` |
| Email, UPI VPA, PAN, IFSC, PIN/CVV | | redacted |

Pattern order matters: longer, more specific patterns run first so a 16-digit card is not first
chewed up by the 10-digit phone pattern.

**This is enforced by test** — one test submits a card number through the API and asserts it
appears in neither the database nor the response.

### Other controls

| Control | Implementation |
|---|---|
| Phone numbers | Salted SHA-256 hash only; the raw number is never written |
| Passwords | bcrypt, with the 72-byte truncation handled explicitly |
| Auth | JWT bearer tokens, role-based dependency `require_role(...)` |
| Privilege escalation | Public registration is forced to `participant`; staff accounts are admin-only |
| Self-lockout | An admin cannot demote or disable their own account (400) |
| Disabled accounts | Refused at login with 403 |
| URL fetching | Never. Static string analysis only |
| Stored URLs | Defanged so they cannot be clicked from a report or the database |
| Rate limiting | In-memory token bucket, 60 requests/minute/IP |
| Scam generation | Refused by the assistant's safety gate |
| Outbound network | None in the default configuration |

### Ethical stance

The app is **advisory only**. Every verdict carries a disclaimer in both languages and the 1930
helpline. It never claims to recover money, and it warns that anyone offering paid recovery is
running a second scam targeting people who have already been cheated.

## 9. Impact measurement methodology

> **Reminder: the figures below are from the seeded demonstration cohort, not real workshops.**
> They illustrate what the system computes. Replace them with your own after running sessions.

### The formula

$$\text{Awareness Improvement} = \frac{\text{Post-test Score} - \text{Pre-test Score}}{\text{Pre-test Score}} \times 100$$

### The division-by-zero guard ⭐

This expression is **undefined when the pre-test score is zero** — and that is not hypothetical.
In the demonstration cohort **10 of 118 participants** score zero on the pre-test, which is
realistic for first-time internet users at a senior-citizens' session.

A naive implementation either crashes with `ZeroDivisionError` or prints `inf`. CyberSathi
returns `null` for the percentage and supplies two alternatives:

| Metric | Formula | Defined when pre = 0? |
|---|---|---|
| Improvement % | `(post − pre) / pre × 100` | ❌ |
| **Absolute gain** | `post − pre` | ✅ |
| **Normalized gain** (Hake's *g*) | `(post − pre) / (max − pre)` | ✅ |

All three appear in the UI, the CSV export and the PDF report, with a plain-language note. Those
rows are **excluded from the mean and median and counted explicitly** rather than silently dropped.

### The mean-skew caveat ⭐

Ratio-based improvement is inflated by small denominators: a participant going from 1/10 to 5/10
registers as **+400%**. The dashboard detects this automatically (mean > 1.15 × median) and
returns a bilingual `interpretation_note` telling you to quote the **median** and **Cohen's d**,
both of which are robust to the distortion.

### Demonstration-cohort results

| Metric | Value |
|---|---|
| Workshops / participants | 6 / 118 |
| Matched pairs (n) | 118 |
| Mean pre-test | 36.44% |
| Mean post-test | 67.03% |
| **Median improvement** | **80.0%** |
| Mean improvement *(skewed — do not headline)* | 101.39% |
| Standard deviation | 84.29 |
| **Cohen's d** | **2.27** (large: 0.8+ is large) |
| Paired t-statistic | 24.65 |
| p-value | < 0.001 |
| Moved from low awareness to aware | 25.42% |
| Undefined improvement (pre = 0) | 10 |
| Feedback | 4.36 / 5 across 47 responses |

The t-test is hand-implemented so the formula can be shown in your report, with SciPy used only
for the p-value. Zero-variance input (every participant gaining identically) correctly returns
`None` rather than an infinite t-statistic.

### Threats to validity — write these yourself before an examiner does

- **Testing effect** — a pre-test primes attention; mitigated by disjoint items
- **Social desirability** — participants may answer as they think you want
- **Self-selection** — those who attend may already be more interested
- **No control group** — improvement cannot be causally attributed with certainty
- **Short interval** — an immediate post-test measures recall, not 30-day retention
- **Sample size and geography** limit generalisation

## 12. Engineering decisions worth defending

These are the questions most likely to be asked, and the answers.

**Why a hybrid instead of pure ML?**
A model cannot explain itself to a 70-year-old, and it is bounded by its training distribution.
Rules carry the bilingual explanation and catch novel scripts. Giving rules 45% means a message
can be flagged on rule evidence alone.

**Why never fetch the URL?**
Fetching confirms to the attacker that a human read the message, and risks executing a payload
on a demo laptop. All 25 features come from the string.

**Why bcrypt directly instead of passlib?**
passlib 1.7.x reads `bcrypt.__about__`, which newer bcrypt releases removed, producing a
confusing version error on a fresh install. Calling bcrypt directly avoids it entirely.

**Why does the retriever cache dicts, not ORM objects?**
SQLAlchemy objects are bound to the session that loaded them. Caching them across requests
raises `DetachedInstanceError` the moment an attribute is touched — a real bug found during
development where the assistant worked on the first request and failed on every one after.

**Why is the risk colour always paired with an icon and text?**
Roughly 1 in 12 men cannot reliably distinguish red from green. Colour alone would exclude them.

**Why is the campaign step personalised?**
The pre-test already reveals which topics this participant does not know. A facilitator with
fifteen minutes should spend them where they count.

**Why report the median and not the mean?**
Ratio improvement is inflated by small denominators. The median and Cohen's d are robust; the
dashboard flags the distortion automatically rather than letting the number stand alone.

## 13. Known limitations

State these before an examiner finds them:

1. **ML metrics are an upper bound** — synthetic training data; no field-tested accuracy yet
2. **No control group**, and the post-test is immediate — it measures recall, not retention
3. **Advisory only** — a "safe" verdict on a novel scam is possible, and the UI says so
4. **Rate limiting is per-process and in-memory** — a multi-worker deployment would need Redis
5. **The default `SECRET_KEY` is for development** — any shared deployment must set its own
6. **Tamil corpus is smaller than English** (298 vs 552 rows); per-language metrics are not
   reported separately
7. **The knowledge base is static** — no live threat feed
8. **QR decoding fails below a luminance range of ~6/255** — genuinely below the noise floor,
   which is why the error message offers pasting the text instead

## 15. How to run it

### Windows, one click

```
SETUP.bat      run once — installs everything, trains the models, seeds the database
START.bat      run every time — starts both servers and opens the browser
```

### Manual

```bash
cd backend
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe ml_training/generate_datasets.py
.venv/Scripts/python.exe ml_training/train_text_model.py
.venv/Scripts/python.exe ml_training/train_url_model.py
.venv/Scripts/python.exe -m app.seed.run --all
.venv/Scripts/python.exe -m uvicorn app.main:app --reload
```

```bash
cd frontend
npm install
npm run dev
```
